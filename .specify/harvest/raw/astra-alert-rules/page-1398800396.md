# To test confluence page id alert rules in experian rca

## ✅ 1. 5XX Errors (API / Backend)

**Trigger **

- HTTP 500, 502, 503, 504 detected.

**Category**
➡️ _Server issue / Application backend failure_

**Validation Rule**

- If alert contains a 5XX error code (500–599) AND the message indicates a failure
(e.g., "unable to connect", "failed", "timeout", "unreachable"),
mark the alert as VALID.If the alert contains 5XX but the message indicates noise
(e.g., "probe failure", "transient", "intermittent", "staging"),
mark the alert as FALSE POSITIVE.Metrics like rate or occurrence count are optional. If not provided,
use message semantics to determine validity.

If below threshold → **FALSE POSITIVE → P5**

**Priority**

- **P1** → Cart, Checkout, Payment, Auth, Recommendations (core services)
- **P2** → Non-critical production APIs
- **P3** → Dev/Staging environments
- **P4** → Intermittent errors auto-recovered, no user impact
- **P5** → Alert triggered due to retries / synthetic monitoring noise

## ✅ 2. Latency Spikes (API Latency > 2s)

**Trigger**

- Latency > 2s for **3 consecutive datapoints**

**Category**
➡️ _Application performance OR Infra bottleneck_

**Validation**

- If CPU > 80% OR Memory > 75% → Infra issue
- If infra healthy → Application bottleneck

**Priority**

- **P1** → Latency + 5XX together
- **P2** → Infra saturation leading to latency
- **P3** → Debug/analytics endpoints
- **P4** → Short-lived latency, self-recovered
- **P5** → Non-user-facing staging traffic

## ✅ 3. Pod Restart Loop (Kubernetes)

**Trigger**

- Restarts > **5 within 10 min**

**Category**
➡️ _Infrastructure / Kubernetes reliability_

**Validation**
Check logs for:

- `OOMKilled`
- `CrashLoopBackOff`
- `ImagePullBackoff`

**Priority**

- **P1** → Production business services
- **P2** → Staging or shared services
- **P3** → Dev/test environments
- **P4** → Node drain/maintenance expected restarts
- **P5** → Autoscaling-driven scheduled restarts

## ✅ 4. Disk Usage Alerts

**Trigger**

- Usage > **84%**

**Category**
➡️ _Infrastructure_

**Validation**

- Ignore if node flagged for decommissioning

**Priority**

- **P2** → > 90%
- **P3** → 85% – 90%
- **P4** → Cold-storage volumes / non-prod
- **P5** → Duplicate, already ticketed or acknowledged

## ✅ 5. Network Errors (Timeout, Connection Refused)

**Category**
➡️ _Network / Connectivity_

**Validation**

- Check multiple services + nodes

**Priority**

- **P1** → Cluster-wide, multi-service impact
- **P2** → One affected production service
- **P3** → Staging-only network disruption
- **P4** → Single retry success, temporary DNS failure
- **P5** → Synthetic probe timeouts, false alarms

## ✅ 6. Business Logic Failures (Logs)

Keywords:

- `"payment failed"`
- `"order creation failed"`
- `"inventory mismatch"`
- “redis failure”

**Category**
➡️ _Application / Business domain_

**Priority**

- **P1** → Payment + Checkout failures
- **P2** → Order processing degradation
- **P3** → Inventory mismatches
- **P4** → Incorrect analytics/metadata
- **P5** → Unused feature workflow errors

# ✅ Categorization Decision Tree

| Indicator | Category |
|---|---|

| Indicator | Category |
|---|---|
| HTTP 5XX, backend stacktrace | **Server issue** |
| Pod restarts, node pressure | **Infrastructure** |
| High latency only | **Application** |
| DNS, routing, connection refused | **Network** |
| Fraud alerts, unauthorized access | **Security** |
| Browser/client request failures | **Client issue** |
| Missing context / unclear logs | **Unknown** |

# ✅ Global Rules

✅ If multiple rules apply → pick **highest severity (P1 worst)**
✅ If insufficient data → **category = Unknown, priority = P5**
✅ Priority NEVER based on guess — only evidence
✅ Business-critical services always prioritized higher
